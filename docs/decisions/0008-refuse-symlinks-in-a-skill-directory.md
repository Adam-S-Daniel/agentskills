# 0008. Refuse symlinks in a skill directory rather than digest them

- **Status:** Accepted
- **Date:** 2026-08-30
- **Deciders:** Adam Daniel

## Context

`digest_skill_dir` (`scripts/generate_skills_lock.py`) and its line-for-line
mirror `digest_dir` (inline in `.claude/hooks/skills-bootstrap.sh`) both walked
a skill directory like this:

```python
for candidate in root.rglob("*"):
    if not candidate.is_file():
        continue  # directories carry no bytes; broken symlinks carry none either
    entries.append((candidate.relative_to(root).as_posix(), candidate))
```

`is_file()` **follows** symlinks. So it is true for a symlink to a file, and
false for a symlink to a **directory** and for a dangling one. Neither of those
two shapes contributed a manifest entry at all — not the link name, not the
target, nothing. Two materially different skill directories could therefore
produce the **same digest**, and the hook would install the tampered one under
a digest that verified.

That comment stated the intent correctly for the dangling case and was silent
on the case that costs: a symlink to a directory is not "no bytes", it is a
whole subtree the walk never sees.

The digest is the primitive the entire delivery design rests on — the README's
"what it installs is pinned and integrity-checked by `skills.lock`", and the
hook's own "an unpinned, unverified fetch is the whole risk". A digest that is
not a commitment to the directory's content makes that verification decorative
for this class. The payload is instruction text the model loads on turn one,
not code, so "it only affects skills" is not a mitigation.

It also chains with the cross-lock union (ADR 0007): the collapse rule treats
identical `(name, digest)` rows from different locks as interchangeable, so a
colliding directory becomes a way for one lock to supply the bytes for another
repo's skill name at a matching digest.

Reported by the isolation/integrity lens of the adversarial round on #131, and
independently graded UNDERSTATED by a skeptic instructed to refute it.

## Decision

**A skill directory may not contain a symlink, in any shape. Both
implementations refuse rather than encode.**

- The generator raises `GeneratorError` and writes no lock — this repo's
  standing posture of not emitting a lock the hook would reject.
- The hook's `digest_dir` exits, printing nothing. Every caller already treats
  an empty measurement as a failure (`may_replace`'s `-n "$have"` guard, the
  install loop's `$got` = `$want` comparison), so the skill fails integrity,
  its unverified bytes are removed rather than left live in `~/.claude/skills`,
  and the verdict reports it. Fail-closed.

`rglob` surfaces all three shapes as entries with `is_symlink()` true and does
not descend into a symlinked directory, so one test placed before the
`is_file()` arm covers the whole class in both copies.

## Why this doesn't break X

The obvious objection is the one #132 raised against fixing it inside a feature
PR: changing the digest **algorithm** changes every digest in every committed
`skills.lock` in the fleet, which needs a coordinated re-pin and hits the same
forward/backward-compatibility trap the `sha256:` prefix rollout had to be
sequenced around — tolerance must reach every consumer *before* the generator
emits anything new, or ephemeral sessions on older pins go `DEGRADED`.

**Refusing is not that change, and the difference was measured rather than
assumed.** Across all three registries that feed a lock in this fleet —
`agentskills` `plugins/`, `cms-platform` `skills/`, and `agentskills-private` —
there are **zero** symlinks under any skill directory. So:

- **Digests:** no digest any committed lock names changes. Verified directly:
  all 9 rows of this repo's own `skills.lock` reproduce byte-identically with
  the guard in place, and `adam/skills-doctor` recomputed under the *original*
  algorithm gives the same number as under the new one.
- **Consumers on an older pin:** a lock generated by the new code is
  bit-identical to one generated by the old, so an older hook reads it exactly
  as before. There is no rollout to sequence, because there is nothing new to
  tolerate.
- **The hook/generator mirror:** both sides changed together, as
  `test_the_hooks_digest_agrees_with_the_generators_on_a_tricky_skill` requires.

The cost is deferred, not avoided: if a bundle ever genuinely needs a symlink,
*that* change carries the migration. It will be visible rather than silent,
because this refuses instead of hashing around it.

One shape was already blocked upstream and is worth writing down so the next
reader does not mistake the coverage: an **absolute**-target symlink never
reaches the digest at all, because `materialize` extracts the pinned ref
through `tarfile`, which rejects "a link to an absolute path". Only a
**relative** symlink reaches the walk — so that is the fixture the tests use.
A test built on an absolute target passes while exercising `tarfile`'s guard
and reporting it as this one.

## How to verify

- `scripts/test_generate_skills_lock.py::test_the_generator_refuses_a_symlink_in_a_skill_directory`
  — parametrised over all three shapes, because the two that were invisible to
  the old walk are the two a single-shape test would most likely have omitted.
- `…::test_the_collision_a_symlink_used_to_buy_is_gone` — asserts #132's actual
  claim (two trees, one digest) directly, with a control that keeps it from
  passing against an implementation that simply refused everything.
- `…::test_both_digest_implementations_refuse_a_symlink` — binds the hook and
  the generator on the input they must both REFUSE, the other half of the
  contract `…agrees_with_the_generators_on_a_tricky_skill` binds on the input
  they must both hash the same. `TRICKY_SKILL` deliberately does not carry the
  symlink: a fixture that is refused cannot also be the fixture proving the two
  agree on a digest.
